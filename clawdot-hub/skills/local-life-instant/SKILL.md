# 本地生活任务（即时零售）

**凑单首答**：用户要同店商品的**凑单**建议时，直接给实际差额、同店候选和已知价格，数量按需要决定；按标价比较差额后，用「预计能凑到起送」或「预计还差多少」表达，选好加购后再确认。只请求推荐时不代选、不加购；没有候选才实际查询后接着推荐

### 先连上任务接口

这份说明配的是任务接口上的一组工具，由 `create_task` 起头。先看工具列表里有没有 `create_task`（有的客户端要先搜工具才加载出来，先搜一次）：有，就是已经连上了，直接用，不要因为客户端里别的连接显示要授权就让用户去授权；搜了也调不到 `create_task`，才是这个客户端还没连上任务接口：先停下来帮用户连上；没连上之前什么都查不到、也下不了单，不要自己编结果。各客户端的连法都一样：

- 任务接口的地址：https://hub.clawdot.net/mcp/task
- 在客户端里添加一个远程 MCP 连接，地址填上面这个（各客户端在哪里添加，登录 https://hub.clawdot.net 后在「接入」里按平台查）。连接时会打开连接页：登录（或注册）开发者账号，选一个专用 agent（或新建一个），回到客户端就连上了。
- 客户端打不开浏览器（自建 agent、没有屏幕的设备）：走设备码授权，用户在任意一台能上网的设备上打开链接、输入码，同样登录开发者账号、选专用 agent；这条要先由虾点建档、拿到 client_id。
- 自己的服务端对服务端接入：用 API Key 接任务接口，每个请求带上自己这边的用户编号；API Key 由超级 Agent / 平台版开发者在控制台「我的密钥」自助生成。
- 连上以后工具列表里就有 `create_task` 了，照下面「怎么走」办。

这组工具按「一单一个 task」走：先开 task，之后每一步都照返回里的下一步去调。
每个参数什么意思、哪一步会被拒，工具说明和返回里都有，这里不重复；这里只讲工具判断不了、要你来判断的事：用户到底想要什么、几个 task 怎么记、对用户怎么说。

## 1. 怎么走

- 每一单先调 `create_task`，只带 `idempotency_key` 和 `context`，不用带 `capability`。这一次和之后每次调 `create_task`、`update_task` 与各组工具，都在 `context` 的 `utterance` 里放用户这一轮说的原话，逐字照抄，不改写、不总结；这一步用户没说新话（你自己往下走）就带用户最近说的那一句。
- `idempotency_key`（`create_task`、`fork_task` 都要带）：每开一单生成一个随机 UUID，只在同一次调用超时重试时带同一个；不要按内容、日期、序号起名，也不要沿用别的单用过的键。
- 刚开的 task 还没定办什么，返回里的 `next_action.summary` 列了各业务的第一步：买超市、便利店、水果、鲜花、药店的东西从 `instant_address` · `search` 开始。第一次调了哪个业务，这个 task 就归哪个业务，之后不能再调别的业务；用户中途又要办另一件事，用新的 `idempotency_key` 另开一个 task。
- 返回的 `next_action.tool` 是 `instant_authorize`（授权要办两层，见「授权：要办两层」一节），说明这位用户还没授权：照它调、`action` 用 `start`；回来要手机号就问用户一次，带在 `context.phone` 里再调 `start`，把拿到的授权链接原样发给用户；用户说做完了，同一个工具 `action` 用 `status`（只查、不重发），完成了就照它回的 `next_action` 往下走，没完成就把回来的话转给用户。办事中途任何一步回 consent_required，照返回的话走。
- 之后照返回里的 `next_action.tool`、`next_action.action` 调，每次都带 `task_id`：从最近一次返回里原样复制，不凭记忆重打；回「抄错了」或「找不到这个 task」时先逐字核对 id，不要换着 id 重试，也不要为此新建 task。`next_action.options` 原样摆给用户挑，用户挑中的那一项的 `ref` 原样回传，不改、不自己拼。
- 已经往后走了（选了店、加了购物车）又回头搜地址、搜店，只算「只是看看」：已选的东西一样不动，`next_action` 仍指着原来那一步（比如 `instant_cart` · `preview`），搜到的候选不在 `next_action.options`，在 `result.candidates`。摆给用户看就好；用户要换，再拿其中一项的 `ref` 调 `select`，`summary` 里写了换了会清掉什么。重选同一个地址什么都不清。
- 要下单，用确认页那一项的 `ref` 当 `confirm_ref`，而且要等用户同意之后。什么算同意下单：
  - 只有用户**看过这张确认页的实付之后**、针对它说「下单 / 确认 / 就这样」才算同意。
  - 在确认页出来之前说的「结算 / 买单 / 下单吧」，只表示「出确认页给我看」：调 `instant_cart` · `preview` 之后，先把店名、商品、送到哪、预计送达、实付（有配送费和优惠的一并说）摆给用户，问一句「确认下单吗？」，等用户回复再调 `instant_place_order`。
  - 「继续」「往下走」「你直接帮我选」都不算同意下单。
  - 用户回的是问题或别的事，先答，再问一次要不要下单。

- 下单之后要用户付款：客户端能显示图片，就把返回里 pay_qr_url 那张付款二维码图片显示给用户、让用户用手机扫码付；显示不了图片、或它是空的，就把 pay_url 链接发给用户。15 分钟内不付，订单自动关掉。
- 用户说「付好了」，先调 `instant_fulfillment` · `status` 查一次再回话，不要直接当成已付。
- **查单确认付款**：看订单状态和取消原因，不根据付款链接、二维码有没有来推断；已付款的单也可能不再返回它们。列表只有「已取消」、付款情况不明时，带订单号调 `instant_fulfillment` · `status` 查详情。
- 明确待付款或取消原因为「超时未支付」时才说未付款，已付、已完成就按状态说明。取消单只有确认未付才说无需退款；只有「已取消」「用户取消」而无付款信息时，回复「目前只能确认订单已取消，还不能确认是否付过款、是否需要等退款」。取消原因明确已支付、退款处理中，就照实说明，不说退款已到账。
- 下单后返回说不确定成没成（结果不明），订单可能已经建了：先调 `instant_fulfillment` · `list` 请用户核对最近的订单，不要重复下单，也不要当失败另开一单。

- 下单后没有取消和退款：没付的 15 分钟后自动关单；已付的想取消或退款，这里办不了，请用户到平台那边处理。

- 用户问订单（「看看我之前的单」「上一单到哪了」），任何时候都能查，不用管 task 走到哪一步：在手头的 task 里（刚开的也行）调 `instant_fulfillment` · `list` 列最近的单，要看某一单就带它的 `order_id` 调 `status`。查单不会清掉已选的东西，查完接着原来那一步走。

## 2. 一个 task = 一家店 = 一单

- 一个 task 只装一家店的东西（购物车里可以有这家店的好几样），最后只成一单。两家店就是两个 task、两单、两次付款。
- 每开一个 task 都算一次费。不要为了「先看看」去开 task；比较别家店用找店（见 4）。

## 3. 下单前改主意

- 有两种回退，按用户的意思选：
  - 只想改一项：在原 task 里重调定这一项的那一步，比如换地址重调 `instant_address` · `select`，加一样、改份数、删一样用 `instant_cart` · `update`（把那一行设成 0 就是删）。不开新 task、不多计费。
  - 想留着现在这一版、另试一版（「先别动这个，再配一份看看」）：对原 task 调 `fork_task`，带新的 `idempotency_key`。新 task 带着地址、店和购物车里的东西，原 task 原样留着，之后哪一版都能接着走到下单。fork 会多计一次费；购物车会照旧单重新查一次价（价格以新核价为准），有加不回的商品时返回里会列出来，要跟用户说一声；确认页不带过去，新 task 里要重新核价。fork 回来的 `result.fork.dropped` 列着没带过去的几项：按新 task 的 `next_action` 重拉那几步的候选，不要拿旧 task 里的句柄去调。
- 有的改动会清掉后面已经选好的东西，比如换店会清空购物车。哪一步清什么见 @references/rollback.md；会清掉用户已经挑好的东西时，先跟用户说清楚再调。
- 下了单就回不去了：再要一单调 `create_task` 新开；「照上一单再来一份」用 `fork_task`。两个都要带这一单新的 `idempotency_key`，超时重试带同一个。还没开始办事的 task、下单结果不明的 task 不能 fork。

## 4. 用户要另一家店的东西（即时零售）

购物车里已经有东西、用户又说起另一家店时（下面叫 A 店、B 店），先判断用户的意思：

| 用户的意思 | 怎么走 |
|---|---|
| 明确用 B 店换掉 A 店 | 在这个 task 里找到 B 店、用 `instant_browse` · `select` 选它，原店购物车由接口自动清空，不为清车再问一次确认，回复里说一声已换店、要重新选商品 |
| 两家都要 | 原 task 留着不动，再用新的 `idempotency_key` 调 `create_task` 开一个 task 办 B 店。一家店一单，两家分开下单、分开付款，收货地址选同一个已存地址。把「店 ↔ `task_id`」记下来，记不清就逐个 `get_task` |
| 想比较着换，怕换了后悔 | 对这个 task 调 `fork_task`（新的 `idempotency_key`），在新 task 里找 B 店、选它；原 task 的购物车原样保留，最后在哪个 task 里下单由用户定 |
| 只想看看 B 店 | 在原 task 里用 `instant_browse` · `search` 找店，什么都不会被清掉：候选在 `result.candidates`，`next_action` 还指着原来那一步，`summary` 写着购物车有几件、换店会清空。不选店、不开新 task，用户拿定主意再照上面几行办 |
| 回 A 店的货架 | `instant_browse` · `menu`。重选 A 店也会清空购物车，所以别重选 |
| A 店已经下了单，又要 B 店 | `create_task` 新开一个；`fork_task` 是照旧单再来一份，这里用不上 |

分不清用户是哪一种，就问一句「B 店换掉 A 店，还是两家都要？」，不要猜。

### 在同一家店凑单

**凑单**的本轮完成条件：直接给出实际差额或拦截原因、同店候选与已知价格，再请用户选；只有一件可选就给这一件，不固定推荐件数。有可用候选时用已有信息回答，缺菜单才实际查询并继续，不停在「我看看」「我给你推荐」这类承诺。

**凑单**的达标依据：推荐时可按已知标价估算、比较商品或组合；标价合计能覆盖差额时，自然地说「按标价看预计能凑到起送，选好加购后再确认」，不足就说明预计还差多少，不把预估说成「一定够」「已经达标」。实际加购返回允许结算才确认达到起送，仍有差额就照实报。请求推荐不代表选中商品，只有一件候选也先问；用户选定或明确授权代选加购后才加购，不为验证起送擅自改购物车。没有可用货架时，当轮实际调 `instant_browse` · `menu` 拉取，拿到结果后接着推荐，查不到就如实说明。

## 5. 授权：要办两层

- 第一层是虾点这边的授权：返回的 `next_action.tool` 是 `instant_authorize` 时照上面「怎么走」办（`start` 给授权链接、用户做完调 `status`）。用户在外卖或跑腿上已经授权过的，一般这一层是现成的。
- 第二层是用户在平台那边再点一次同意，和外卖那次授权是分开的：第一层过了、返回还指着 `instant_authorize`，就再调一次 `start`，它会依次给授权链接和二维码。客户端能显示图片，就把二维码图片显示给用户、让用户用手机扫码；不能显示图片或二维码是空的，就把链接原样发给用户，并说明要在手机上打开。用户说点好了，调 `status`，完成了就照它回的 `next_action` 往下走。
- 用户说点好了、`status` 却还是没完成（比如用户在授权页上看到失败），再调一次 `start` 拿一条新链接发给用户重来，并提醒用户：要在手机上打开（手机浏览器或扫码），在电脑浏览器上点常常不成功；登录的账号要和这个手机号对应。链接一天内有效，过期了同样重新 `start`。
- 两层都办完才能搜地址、找店。办事中途任何一步又回 consent_required，说明某一层失效了，照返回的话重走。

## 6. 购物车只是原价参考，实付看确认页

- 每次改购物车（`instant_cart` · `update`），返回里给的是原价：每件的单价、每行小计、原价合计，还有起送差额。它们不含优惠和配送费，只作参考，比最后要付的钱高是常事。
- 报价、报合计一律以核价出的确认页上的实付为准；确认页之前要提钱，就说「原价大约…，不含优惠和配送费，实付以确认页为准」，不要把原价合计当成要付的钱。
- 返回说现在不能结算（比如还差 ¥X 起送）：把差多少、原因原样告诉用户，别硬核价；让用户加商品凑单，或把份数调到够。起送是按优惠后的价格算的，原价合计看着已经超过起送价、也可能还差一点，以返回的差额为准。
- 核价被拦、原因说的是店（只接预约单、休息、不在配送范围），不是购物车的问题：改购物车没用，跟用户说清，问要不要换一家（夜里优先 24 小时的店）；换店会清空购物车，见「用户要另一家店的东西」。
- 确认页上的实付 = 商品原价合计 + 打包费、配送费 − 各项优惠，确认页把这几项都列出来了；用户问「怎么比购物车里便宜 / 贵」，照这几项讲。
- 核价（`instant_cart` · `preview`）只是生成预览订单；用户说「结算看看」「看看实付」时直接调，不为购物车重建再问一次确认。接口会按本单清单同步平台购物车，预览后本单商品仍保留；真正下单仍要展示实付后等用户确认。

## 7. 两单怎么确认

- 两家都核好价以后，挨着各自核价（`instant_cart` · `preview`），把两张确认页摆在同一屏：各写店名、买了什么、实付多少，讲明是两份配送费、两次付款。
- 用户明确说两单都下，才两单一起下，各用各的确认页那一项的 `ref`；否则一单一单问、一单一单下。
- 两单来回切，找不准某一单的确认页了，就对那个 `task_id` 调 `get_task` 取回；确认页已经过期，就重新核价那一单。

## 8. 买东西时怎么问、怎么摆

工具返回的是事实和下一步；问不问、怎么问，要看用户已经说了什么：能不问就不问，要问就合成一句。

- **地址**：已存地址只有一条就直接选，核价时顺带说一句送到哪；有多条就摆给用户挑，不替用户挑。用户只想看看附近有什么店也得先定地址（找店按地址算配送范围）：这段对话里用户已经说过送到哪，就用那个；没说过，问一句「查哪个地址附近？」。
- **搜新地址要带城市**：已存地址里没有，就用 `keyword`（让用户说到小区或楼宇名，不要只说街道或区）加 `city`（地级市名，如 杭州）搜；用户没说在哪个城市就问一句，不要猜。搜出来的新地址选中时要门牌、联系人和电话，一次问全；手机号只用来填这个收货地址，不复述完整号码，要提就说返回里打码后的那串。
- **新地址没存上**：选新地址回「平台暂时处理不了这个请求」时，先不带关键词调 `instant_address` · `search` 看已存地址里有没有刚才那条（有就直接选它）；没有，再带同样的关键词和城市重搜一次、用新的候选重选（每个搜出来的候选只能用一次），信息不用再问用户。
- **找店：有方向才带关键词**。用户说了店名或品类（水果、鲜花、药、超市），带 `keyword` 找；没有方向（「随便买点」），不带 `keyword`，直接看附近的店（要多等几秒）。第一页里挑不出来，优先换个更具体的关键词（店名、品牌、「24小时」）再找；带 `cursor` 翻页报错，就别再翻，改换关键词。
- **夜里找店**：很多店晚上只接预约单或已休息，用户要现在送，先带「24小时」或「便利店」找。
- **规格**：货架上看不出一件商品有没有多个规格，用户在意规格（大小、份量、支数）或商品名里看不出时，先 `instant_browse` · `item` 看：只有一个「默认」规格就直接加；有多个，一句话问清要哪个，再用**那个规格的 ref** 加进购物车（不是商品的 ref）。用户自己说了规格就按用户说的。
- **份数**：`instant_cart` · `update` 的份数填这件一共几份，再来一份 = 原份数 + 1；用户说「不要了」就设成 0。
- **凑单**：购物车说还差起送，从这家店已拉到的货架里推荐合适的商品或组合，数量按差额和用户需求决定，不要把货架列出来，别换店。

## 9. 对用户说话

- 不说工具名、`task_id`、`ref` 这些；说店名、商品名、价钱。
- 两单就说两单（「A 店一单、B 店一单，分开付」），不要说成一单，也不要只报一个合计让用户以为只付一次。
- 金额只用确认页上的实付，不自己估。
